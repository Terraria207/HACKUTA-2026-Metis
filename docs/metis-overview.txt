Metis (Mathematical Exploration of Topics to Identify Similarity) — Mathematical
Connection Explorer
Summary
Metis's goal is to find new mathematical connections: relationships between concepts
that nobody has stated yet, especially ones that bridge distant fields. It starts from a
single mathematics paper and looks for links between that paper's ideas and the rest of
mathematics. It breaks the paper into concepts (axioms, definitions, theorems), places
them in a graph of existing mathematics, and sends a crew of four AI models to propose
new logical links. A proof reviewer (Penelope) checks every proposed link, a prover
(Hephaestus) tries to prove the promising ones in Lean, a researcher (Tiresias) checks
whether it is already known, and an orchestrator with long-term memory (Odysseus)
ranks the ones that survive.
The output is an updated concept graph and a short ranked report of the most promising
candidates for new mathematics: connections that aren't found in the literature. Users
work in journeys: each starts from shared, prebuilt base modules for its chosen islands,
takes papers one at a time and can be resumed later (see User interface).
Data model
The graph has two layers: a tree of groups that says where each concept lives, and typed,
directed edges (some with several premises) that say how concepts relate logically.
Group tree
A rooted tree built from MSC 2020, limited to the demo islands (e.g., linear algebra,
graph theory, probability). Each island's groups are prebuilt (see Base graph); within a
journey, Odysseus can add more (see Odysseus).
Depth 0: root (all of mathematics)
Depth 1: fields (islands)
Depth 2: subfields (regions)
Depth 3: subtopics (villages)

Concepts (Nodes)
A concept is an axiom, definition, theorem or other math concept on a fundamental
level.
Each concept has exactly one home group: the deepest group that fits.
Each concept and each group has a short description, used for matching new
concepts and for measuring content similarity.
Where nodes come from
Normally, nodes come from two sources: the gods (base concepts) and paper
decomposition (every paper, including each input paper, is decomposed when it is
added to the tree). A paper's genuinely new concepts are then integrated: linked to
existing nodes, with integration nodes added where a link needs a standard concept
the graph lacks (see Per-paper pipeline, step 1).
In special circumstances, a crew mate may create a new node: when a proposed
connection needs an intermediate concept (e.g., a lemma, definition or construction)
that is in neither the graph nor the papers.
The new node must be part of at least one proposed edge, as a premise or
conclusion; no standalone nodes.
It is placed in an existing home group, with a short description and, where
possible, a source that defines it.
Penelope checks that it is well defined and isn't a duplicate of an existing node.
Tagged source = the crew mate that created it.
If no existing group fits a new node, it is held back and flagged for Odysseus, who
decides whether to add a new group for it.
Odysseus may also propose a completely new node when a pattern across papers
points to a missing concept. These are checked most heavily and start as Proposed
(see Odysseus, Proposing new nodes).

Proposed nodes are quarantined: they and their edges don't count toward graph distance,

has nothing to prove.
Edges
Concepts are connected by typed edges, each representing a logical relationship (e.g.,
implies, generalizes, is a special case of, is equivalent to, is defined from).
Direction
An edge's direction follows the logic: it points from what is assumed to what follows.
A → B means A gives B.
If the logic works both ways (an equivalence, A ⇔  B), the edge is undirected.
Directed hyperedges
A directed edge can have several premises and one conclusion. This is a directed
hyperedge: all of its premises together give the conclusion (AND). It is drawn as
several lines converging on the conclusion.
Separate edges into the same node mean something different: each one alone gives
the conclusion (OR).
An ordinary directed edge is the one-premise case. An undirected edge always links
exactly two nodes.

Tier and existing tag answer different questions: the tier says how well an edge is
supported, the tag says whether anyone has stated it before. An intuitive edge tagged
Not found is a possible new result. A verified edge tagged Not found is a proven new
result.
Proofs
Because every edge is a logical step, edges combine into proofs. To reach a
conclusion, every premise of the edge that gives it must itself be reached, or be a
starting concept.
A proof is therefore a tree of edges (more generally a DAG, when one result is used
more than once), not a single chain. A chain is the special case where every edge has
one premise.
Directed edges are followed only in their direction; undirected edges can be followed
either way.
A proof is only as strong as its weakest edge: its tier is the lowest tier of any edge in it.
A proof made entirely of verified and cited edges is a complete logical argument; one
containing any intuitive edge is a conjecture.
Distance measures
Content similarity: how close two concepts' descriptions are, measured by
embedding similarity (0 to 1) of their Voyage AI embeddings (see Storage).
Tree distance: how far apart two concepts' home groups are, from the depth of their
lowest common ancestor (LCA). Tree distance = 3 − LCA depth.
0 = same subtopic, 1 = same subfield, 2 = same island, 3 = different islands.

Graph distance: the length of the shortest path between two concepts in the
concept graph, measured before the proposed edge is added. Direction is ignored
here: a concept that only feeds into another still counts as close to it. A hyperedge
puts each of its premises at distance 1 from its conclusion.
Only verified and cited edges count, so an unproven intuitive edge can't make a
gap look already closed.
Capped at a maximum D_max; concepts with no such path get D_max.
Bridge score
A proposed edge is most valuable when its nodes are similar in content but far apart in
both the tree and the graph. For a hyperedge, the score is computed between each
premise and the conclusion, and the highest is used; Penelope's necessity check keeps an
irrelevant far-off premise from inflating it.
\text{bridge score} = \text{content similarity} \times \left( w_t \cdot 
\frac{\text{tree distance}}{3} + w_g \cdot \frac{\text{graph distance}}
{D_{\max}} \right), \qquad w_t + w_g = 1
Tree distance rewards connections that cross islands. Graph distance rewards
connections the graph doesn't already imply, including ones inside a single island.
The weights are tunable; start at w_t = w_g = 0.5.
A node that isn't yet connected to the rest of the graph by verified or cited edges (an
unintegrated paper concept, or a crew-created node linked only by intuitive edges)
has no meaningful graph distance, so bridge scores involving it use tree distance
alone (w_t = 1) until it is connected.
Distance bands
Bands are measured from the input paper's position in the tree (its primary MSC code).
They are used to draw each crew mate's random groups and papers; a paper's band comes
from its primary MSC code.

Storage (MongoDB)
The graph, the papers and every agent's records live in one MongoDB Atlas database, so
the graph persists between runs and Odysseus's memory survives across them. The
graph has two layers. The base layer holds the island and bridge modules and is shared
read-only by every journey. The journey layer holds everything a journey adds, and every
document in it carries that journey's id, so journeys stay separate. Queries read a journey's
modules together with its own layer. A paper's decomposition is cached, so a paper used
in several journeys is decomposed and reviewed only once.

Per-paper pipeline
Each run takes one input paper, within a journey, through seven steps, from
decomposition to a ranked graph update. The graph persists between runs in MongoDB:
every paper is placed in the tree and decomposed when it is added, so a run starts with all
earlier papers' concepts already in the graph, and each run adds to it.
1. Decompose, add and integrate the input paper.
The paper is broken into concepts and edges by a decomposer model (Gemini 3.5
Flash), and each concept is placed in its home group.
Each extracted concept is first matched against existing nodes (the concept
vector index, then a quick model check on close matches). A match links the
paper to the existing node instead of creating a duplicate; only genuinely new
concepts become new nodes. Without this, every paper would sit apart from the
rest of the graph.
If the paper has no MSC codes (many arXiv papers don't), the decomposer
assigns them; the UI shows them for correction before the run.
Edges the paper proves are tier cited, with the paper as the source. They still go
through Penelope's checks, since decomposition can misread a paper.
Integration of new concepts. Matching covers concepts the graph already has,
but a genuinely new concept would still touch only its own paper's other
concepts, so graph distances to it would mean nothing. Each new concept is
therefore connected to the existing graph (the nodes that were there before this
paper) before the crew starts:
The decomposer extracts what the paper says each new concept rests on and
leads to: for a definition, the concepts it is defined from (one hyperedge into
it); for a theorem, the known results it uses and any known result it
generalizes, specializes or implies. These edges attach to existing nodes
wherever matching finds them, and are tier cited, with the paper (and any
reference it cites there) as the source.
When a link needs a standard concept the graph lacks (e.g., a lemma or
definition the paper recalls from the literature), the decomposer adds it as an
integration node: Established, with the paper's reference as its source,
matched and placed like any other concept, then linked onward the same way.
This repeats until the chain reaches existing nodes, up to a set number of
levels (tunable; start at 2).

Integration edges and nodes go through Penelope like the paper's other
edges; an integration node must also be well defined and not a duplicate. They
are structure, not findings, so they don't enter the ranked report.
A concept that still has no verified or cited path to the existing graph is
marked unintegrated and flagged in the UI. It still takes part in the run, and
later edges can connect it; until then, bridge scores involving it use tree
distance alone (see Bridge score).
2. Draw three random targets (groups or papers) for each crew mate, one per
distance band.
Each crew mate draws its own targets, one per band (see Distance bands).
Each target is either a group or a single paper, chosen at random by a set ratio
(tunable; start at 50/50).
A group: everything filed there, including base concepts and concepts from
earlier papers. Only groups that already hold concepts are drawn.
A paper: only that paper's concepts.
No two crew mates draw the same target, unless a band has too few to go around.
Mixing the two keeps the input paper from being compared only with other
papers, while still allowing direct paper-to-paper comparisons.
3. Crew exploration (see The crew).
Each crew mate compares the input paper against each of its three targets
independently: it reads the input paper's concepts alongside the target's
concepts (the group's or the paper's) and proposes new edges between them
under its perspective.
To keep each comparison within a crew model's context and the run's cost
bounded, a target contributes at most K concepts (the ones most similar to the
input paper's concepts, found by vector search within the target), and each
comparison returns at most P proposals, the crew mate's strongest. K and P are
tunable; start around 50 and 5.
In special circumstances, a crew mate may also create a new node (see
Concepts).
4. Proof review (see Penelope).
Penelope checks every proposed edge and any new node.
5. Formal proof attempt (see Hephaestus).
Hephaestus tries to prove the most promising intuitive edges in Lean. A compiled
proof whose statement Penelope confirms makes the edge verified.

What a crew mate submits for each proposed edge
The edge's nodes: its premises (one or more) and conclusion, or the two nodes of an
undirected edge. A new node (special circumstances only; see Concepts) also gets a
home group (an existing one), a short description and, where possible, a source that
defines it.
The edge type and the claimed tier.
The evidence. Every proposal includes a written argument for how the premises give
the conclusion, since Penelope's correctness check and Hephaestus's proof attempt
both start from it. The claimed tier is set by the strongest evidence attached:
A mathlib reference (the declaration name) → claims verified.
A citation (source plus exact location, such as a theorem number or page) →
claims cited.
The argument alone → claims intuitive.
Crew mates don't write Lean proofs; Hephaestus does that after review.
If the strongest evidence fails Penelope's check, the edge falls back to the next
one (e.g., a citation that doesn't state the result leaves the edge intuitive on its
argument). This is her pass-with-downgrade outcome.
The excerpts from the input paper (and from the target paper, when the target is a
paper) the proposal relies on.
Penelope (proof reviewer)
Penelope, GPT-6.1 Sol, reviews every proposed edge before Odysseus sees it. Like her
loom, she undoes whatever doesn't hold up.
She is a goldfish: each edge is reviewed in a fresh context, without seeing which
model or perspective proposed it or how many crew mates proposed the same edge.
Her judgment rests on the evidence alone; counting agreement is Odysseus's job.
What she receives

The proposed edge: its premises and conclusion (statements and descriptions),
whether it is directed, the edge type and the claimed tier.
The crew mate's evidence and the paper excerpts it cites.
What she checks
1. Well-formed: every node on the edge exists in the graph or is a valid new node, and
the edge type fits the relationship. A new node must meet the special-circumstances
rule (see Concepts): needed for this connection, well defined, in an existing group (or
held for Odysseus's decision on a new group), and not a duplicate of an existing node.
2. Not a duplicate: the edge isn't already in the graph. Two edges are the same when
they have the same premises, conclusion and direction. If it is, it isn't added again: it
goes to Odysseus as further support for the existing edge, and as evidence for
promotion if its evidence is stronger. Recurring support across runs is what
Odysseus's new-node trigger counts.
3. Correct: the claimed relationship holds. The hypotheses match, the argument isn't
circular, and there is no known counterexample. The direction is right, and an
undirected edge holds both ways. For a hyperedge, the premises together are
sufficient and each one is necessary; an unnecessary premise is grounds for
rejection, since it makes a result look more connected than it is.
4. Tier matches evidence:
Verified: the result is in mathlib, or the submitted Lean proof compiles against
mathlib (checked by running Lean, not by judgment), and its Lean statement says
the same thing as the edge.
Cited: the cited source exists and actually states the result, with matching
hypotheses.
Intuitive: the argument is coherent and specific, with no known counterexample.

Hephaestus (Lean prover)
Hephaestus, Leanstral 1.5, turns promising intuitive edges into machine-checked proofs.
Like the smith whose work holds exactly, his proofs either compile or they don't.
He works on intuitive edges that passed Penelope's review, highest bridge score first,
within a set budget per run (tunable).
For each edge he writes the Lean statement (premises to conclusion) and tries to
prove it against the mathlib version the journey's modules were built from.
If the proof compiles, Penelope checks that the Lean statement says the same thing
as the edge, since a proof of a slightly different statement proves nothing about the
edge. If it matches, Odysseus promotes the edge to verified.
If he fails, the edge stays intuitive; a failed attempt is not evidence against it.
He also formalizes Odysseus's proposed definitions for their type-check, and can
attempt proofs of accepted conjectures.
He is a goldfish: each edge gets a fresh context, without knowing who proposed it.
Tiresias (literature researcher)
Tiresias, Gemini 3.5 Flash with Google Search grounding, checks whether each
connection that passed Penelope's review is already known. Like the seer Odysseus
consults in the underworld, he reports what others have already seen.
He is a goldfish: each edge is researched in a fresh context, without seeing which
crew mate proposed it.
He researches intuitive edges and newly Lean-proven ones. Cited edges and edges
already in mathlib are tagged Existing automatically, since their evidence is already a
published statement of the result.

Odysseus (orchestrator)
Odysseus, Claude Opus 5.5, merges, ranks and remembers what the crew finds.
Elephant vs. goldfish
Crew mates are goldfish: each run starts with a fresh context, so they judge the
material without carrying over earlier conclusions.
Odysseus is the elephant: he keeps a persistent memory across papers and runs, so
he sees long-term patterns no single crew mate can.
What Odysseus sees
Only findings that have passed Penelope's review, never the raw papers.
Penelope's pass, downgrade and reject counts for each model–perspective pair.
The full concept graph, including earlier runs' edges, tiers and outcomes.
Metadata on each edge: which model and perspective found it, its distance band,
whether its target was a group or a paper, its bridge score, its existing tag and its
evidence (including any source Tiresias found).
What Odysseus doesn't see
Paper text. This keeps his judgment based on the evidence the crew reports, not his
own first impressions.
Responsibilities
Merge duplicate findings, and treat the same edge proposed independently by

Tracks which model–perspective pairs produce edges that hold up, and can weight

Notices recurring intuitive bridges between the same two islands across different

His memory is kept in MongoDB (the memory and reviews collections; see Storage),

reliability is shared across journeys, since it describes the models, not the
mathematics.
Proposing new nodes
Odysseus can propose a completely new node: a definition or conjecture that explains a
pattern he sees across papers and runs. Because he is inventing rather than extracting,
his nodes get the heaviest checks in the system.
Trigger: a pattern, never a single finding. At least three intuitive edges, from different
papers or runs, must point at the same missing idea (the threshold is tunable).
Checks, in order; failing any one rejects the node:
1. Penelope, with a stricter bar: the node is well defined, not trivial, and not a
renamed copy of an existing node.
2. Tiresias checks the node itself against the literature. If he finds it, it becomes an
Established node with its source, reported as a rediscovery, and the remaining
checks are skipped.
3. Blind testing by the crew: the node goes to crew mates in fresh contexts, without
saying where it came from. The edge-case crew mate tries to break it, and the
others try to connect it to the graph. It needs edges from at least two different
crew mates that pass Penelope (tunable).

4. Optional: Hephaestus formalizes a definition in Lean and it is type-checked. For a

User interface
The interface is organized around journeys. A journey is one exploration: its own base
graph, the papers run through it and everything the agents found. Users can start a new
journey, return to an old one where they left off, and browse the best discoveries across
all of them.

Live trace (the agents' string of thought): a timeline of the run, grouped by pipeline
